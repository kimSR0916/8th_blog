KeepGo에서 추천 코스를 누르면 지도에 장소와 도보 경로가 나옵니다. 도보 경로는 외부 API에서 받아 오므로 시간이 걸립니다. 그동안 장소 사이를 **직선 점선으로 먼저 그렸다가 실제 경로로 바꿨고**, 이 변화가 깜빡임처럼 보였습니다.

## 경로를 못 받은 것과 받는 중은 다르다

원래 화면이 아는 상태는 "경로가 있다"와 "없다" 둘뿐이었습니다. 없으면 직선을 그렸습니다. 문제는 "없다" 안에 성격이 다른 두 상태가 섞여 있다는 점이었습니다.

| 상태 | 화면 |
| --- | --- |
| 받는 중 | 장소 사이에 선을 그리지 않음 |
| 받음 | 도보 경로를 실선으로 그림 |
| 받지 못함 | 직선 점선으로 대신함 |

그래서 훅이 경로와 함께 로딩 여부를 돌려주게 했습니다.

```ts
return {
  path: data ?? null,
  loading: points !== null && isLoading,
};
```

직선은 경로가 없고 **받는 중도 아닐 때만** 보입니다. 호출이 실패하면 그때 직선이 나오므로 지도가 비어 있지 않습니다.

## 누르기 전에 받아 둔다

받는 동안 선을 감추기만 하면 빈 지도를 기다리게 됩니다. 사용자는 후보 목록을 먼저 보고 하나를 고르므로, **목록이 나올 때 경로를 미리 받기**로 했습니다.

```ts
for (const points of keys.split('|')) {
  void client.prefetchQuery(walkQueryOptions(points));
}
```

상세 화면과 미리 받기가 같은 `queryKey`를 쓰기 때문에 이미 받은 경로는 다시 요청하지 않습니다.

## 하루 호출 한도를 아낀다

경로 API는 무료 플랜이라 하루 호출 한도가 있습니다. 미리 받기는 보지 않을 후보까지 요청할 수 있어서 몇 가지 제한을 뒀습니다.

- 앞쪽 후보 4개까지만 미리 받습니다.
- 받은 경로는 브라우저에서 한 시간 동안 다시 씁니다.
- 서버(BFF)도 같은 좌표 조합의 결과를 한 시간 동안 메모리에 둡니다.
- 실패해도 자동으로 재시도하지 않습니다.
- 장소가 2~5곳이고 한국 안의 좌표일 때만 요청합니다.

API 키를 브라우저에 노출하지 않으려고 호출은 BFF에서 합니다. 사용자의 출발지는 외부로 보내지 않고 장소 좌표만 보냅니다.

## 지도는 다시 만들지 않는다

경로가 늦게 도착할 때 지도 컴포넌트를 새로 만들면 또 다른 깜빡임이 생깁니다. 그래서 선만 바꾸고, 새 경로가 이미 보이는 범위 안이면 지도의 확대 수준도 그대로 둡니다.

## 배운 점

느린 요청을 빠르게 만들 수 없을 때도 화면은 나아질 수 있습니다. 상태를 정확히 나누고, 사용자가 다음에 할 행동보다 한발 먼저 받아 두고, 그 비용에 상한을 두는 것이 이번 변경의 전부였습니다.

지연 시간을 전후로 측정하지는 않아서, 얼마나 빨라졌는지 숫자로 말할 수는 없습니다.
